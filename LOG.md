# LOG

A running log of everything done to build this repo, in order.

## Decisions so far

(The first two were reversed later: see
[Generic images](#generic-images-configuration-moves-to-the-stick-2026-10-24)
at the end. Nothing is baked into an image anymore.)

 * Secrets are stored unencrypted in a git-ignored `secrets/` directory.
 * The built ISO contains secrets, so it is written into `secrets/` too.
 * The ISO boots non-interactively (no passphrase prompts); physical
   possession of the ISO/USB is the security boundary.
 * The WireGuard private key is prepared uniquely for this image and
   provided by the user (not generated by the build).
 * Scope: a stock Arch installer that comes up online (WiFi via iwd),
   connects to the WireGuard VPN, and runs sshd with baked-in
   `authorized_keys`, so the install can be driven remotely over SSH.

## More decisions

 * Profile strategy: the repo holds only our overlay files. The build
   script copies a fresh `releng` profile from
   `/usr/share/archiso/configs/releng` at build time and lays our files
   on top, so we track upstream automatically.
 * Secrets are written in their native formats (iwd `.psk` files,
   wg-quick `wg0.conf`, OpenSSH `authorized_keys`), no templating.
 * sshd listens on all interfaces, key-only authentication.
 * Hostname: `arch-iso`.
 * Wired ethernet is preferred; WiFi is the fallback when there is no
   wired route.

## Notes on the stock releng profile (archiso 91)

 * Networking is `systemd-networkd` + `iwd` + `systemd-resolved`.
 * `20-ethernet.network`, `20-wlan.network`, `20-wwan.network` all
   DHCP, with route metrics 100 / 600 / 700, so ethernet is already
   preferred over WiFi when both are up.
 * `iwd.service` and `sshd.service` are enabled.
 * `/etc/ssh/sshd_config.d/10-archiso.conf` enables root password
   login; root's password is empty, so SSH is unusable by default.
 * `systemd-resolvconf` is already in `packages.x86_64`, so a future
   `DNS =` line in `wg0.conf` will work with wg-quick.
 * `wg-quick@.service` sets `WG_ENDPOINT_RESOLUTION_RETRIES=infinity`
   and orders after `network-online.target` and `nss-lookup.target`, so
   a DNS-name `Endpoint` is retried until it resolves. No override needed.
 * `sshdgenkeys.service` only generates host keys that are missing, so
   baked-in host keys are kept.
 * mkarchiso copies `airootfs/` with `--no-preserve=ownership,mode`:
   everything becomes root-owned with default modes unless listed in
   `file_permissions` in `profiledef.sh`. Every secret needs an entry.
 * archiso 91 builds rootless (via `unshare --map-auto --map-root-user`)
   when the user has `/etc/subuid` and `/etc/subgid` ranges, so no sudo.
   (No longer used: builds now run inside Podman.)

## Further decisions

 * WiFi fallback uses the stock route metrics (WiFi may join while wired,
   but ethernet carries traffic). No custom failover logic.
 * SSH host keys are generated once into `secrets/ssh/host/` and baked
   in, so the fingerprint is stable.
 * Build entrypoint: `just build`, which wraps `./build.sh`.

  etc/systemd/system/arch-iso-webhook.service   # boot report webhook

Secrets layout (git-ignored):

```
secrets/
  wifi/<SSID>.psk                 # iwd network files, one per network
                                  # (.psk/.open/.8021x; other files ignored)
  wireguard/wg0.conf              # wg-quick config for this image
  ssh/authorized_keys             # keys allowed to SSH in as root
  ssh/host/ssh_host_*_key[.pub]   # generated by build.sh if missing
  webhook.env                     # optional: WEBHOOK_URL=...
  build/                          # (removed: staging now lives in the container)
  out/                            # built ISOs
```

`build.sh` steps:

 1. Check required secrets exist, and that `wg0.conf` sets
    `PersistentKeepalive` (needed so the peer can reach us through NAT).
 2. Generate SSH host keys into `secrets/ssh/host/` if missing.
 3. Copy releng to `secrets/build/profile/`, overlay `airootfs/`, append
    `packages.extra`, set `iso_name="arch-iso-CONTAINS-SECRETS"`.
 4. Install each secret into the profile's airootfs and append a
    `file_permissions` entry for it to `profiledef.sh`.
 5. Run `mkarchiso -v -w secrets/build/work -o secrets/out` rootless.
 6. Remove `secrets/build/`.

## `just config`: secret templates

```
just config
```

Runs `config.sh`, which creates each missing secret as a commented-out
template (mode 600, directories 700) and never overwrites existing files:

 * `secrets/wireguard/wg0.conf` - wg-quick `[Interface]`/`[Peer]` example
   including `PersistentKeepalive = 25` and an optional `DNS =`.
 * `secrets/ssh/authorized_keys` - an example `ssh-ed25519` line.
 * `secrets/wifi/EXAMPLE.psk.example` - only if no network files exist.
   Copy it to `<SSID>.psk`.

iwd `.psk` format (see `iwd.network(5)`):

```
[Security]
Passphrase=your wifi password

[Settings]
Hidden=true
```

`[Settings]` is optional; `Hidden=true` is only for hidden SSIDs. iwd
does not support trailing comments, so keep comments on their own lines.

Filename is the SSID as-is if it contains only letters, digits, space,
`-` and `_`; otherwise `=` followed by the SSID bytes in hex:
`echo "=$(printf '%s' 'Café' | od -An -tx1 | tr -d ' \n').psk"`.

`build.sh` changes to go with it:

 * Only `*.psk`, `*.open` and `*.8021x` files in `secrets/wifi/` are
   baked in, so the `.example` template is ignored.
 * Templates that are still all comments are rejected: `wg0.conf` must
   have an uncommented `[Interface]` and `PrivateKey`, and
   `authorized_keys` must have at least one non-comment line.

Tested in a scratch copy with no secrets (templates created, second run
overwrites nothing, build rejects each unfilled template), then rebuilt
with the real secrets: one WiFi network baked in at `0/0 600`.

## Boot webhook

Goal: once the network and WireGuard are up, POST a message with the
native and WireGuard IP addresses to a webhook. If WireGuard fails,
send the message anyway with the error.

Decisions:

 * Receiver: a matrix-hookshot generic webhook, sent as
   `Content-Type: text/plain` (hookshot decodes any `text/*` body; see
   https://matrix-org.github.io/matrix-hookshot/latest/setup/webhooks.html).
 * "Native IP": LAN address(es) of the interface with the default route,
   plus the public IP from `https://ifconfig.me`.
 * "WireGuard up" means a handshake with the peer; give up after 2 min.
 * The URL lives in `secrets/webhook.env` as `WEBHOOK_URL=...`.

Pieces:

 * `airootfs/usr/local/bin/arch-iso-webhook` - waits up to
   `WG_HANDSHAKE_TIMEOUT` (120s) for `wg show wg0 latest-handshakes` to
   report a handshake, builds the message, POSTs it with curl
   (`--retry 30 --retry-delay 10 --retry-all-errors`).
   * LAN: default route of the *main* routing table, so a full-tunnel
     WireGuard config does not hide the LAN interface.
   * Public IP: `curl --interface <lan dev> https://ifconfig.me`, again so
     it reports the native connection rather than the VPN exit.
   * On failure: wg-quick unit state, whether `wg0` exists, its address
     and endpoint, and the last 5 journal lines of `wg-quick@wg0`.
   * `--dry-run` prints the message instead of POSTing.
 * `airootfs/etc/systemd/system/arch-iso-webhook.service` - oneshot,
   `After=network-online.target wg-quick@wg0.service` (only `Wants`
   the network, not the tunnel, so it still runs if wg-quick fails),
   `ConditionPathExists=/etc/arch-iso/webhook.env`,
   `EnvironmentFile=/etc/arch-iso/webhook.env`. Always enabled; it only
   runs when the env file was baked in.
 * `build.sh`: registers `file_permissions` 755 for the script (mkarchiso
   does not preserve modes); bakes `secrets/webhook.env` into
   `/etc/arch-iso/webhook.env` (dir 700, file 600) only if it sets a
   `WEBHOOK_URL`, otherwise warns "webhook disabled".
 * `config.sh`: templates `secrets/webhook.env` (commented out).

Example message:

```
arch-iso is up (arch-iso-CONTAINS-SECRETS 2026.10.24)
LAN: 192.168.1.50/24 on enp1s0
Public: 203.0.113.4
WireGuard: 10.0.0.2/32 on wg0 (handshake 3s ago)
```

Tested with `--dry-run` on the build VM: failure path (no wg0) and
success path (stub `wg` reporting a handshake). Found and fixed:
`hostname` is not always installed, so the script uses `uname -n`.
Rebuilt: unit, enable symlink and 755 script are in the image; with the
template still commented out the build warns and leaves the env file out.

## Build inside Podman

Decision: the ISO is always built inside an Arch Linux container with
Podman (even on an Arch host), so the build works from any Linux distro
and the host only needs `podman` and `just`. macOS is out of scope.

```
sudo pacman -S --needed podman
```

Installed: `podman 6.1.4-1` (rootless, overlay storage, netavark).

The host now only needs `podman` and `just`. `archiso`,
`wireguard-tools` and `qemu-base` on the build VM are no longer used
by the build.

How `just build` works now (`build.sh` has two modes):

 1. **Host:** check the secrets (same checks as before), then run
    `podman run --rm --privileged` on `docker.io/library/archlinux:latest`
    (override with `ARCHISO_IMAGE`), bind-mounting the repo at `/build`
    and a named volume `archiso-wireguard-pacman-cache` at
    `/var/cache/pacman/pkg`, with `ARCHISO_WIREGUARD_IN_CONTAINER=1`.
    Secrets are only bind-mounted, never copied into an image.
 2. **Container:** `pacman -Syu archiso openssh`, generate SSH host keys
    if missing, stage the profile and secrets in `/tmp/archiso-build`
    (inside the container, gone with `--rm`), run `mkarchiso` as an
    unprivileged `builder` user, then copy the ISO to `secrets/out/`.

Rootless Podman maps container root to the host user, so files written
by container root (ISO, host keys) are owned by the host user.

### Problems hit and fixes

 * **pacstrap can't mount devtmpfs.** First container build, running
   mkarchiso as container root, failed:
   `mount: .../airootfs/dev: permission denied` /
   `failed to setup chroot`. As root, pacstrap's `chroot_setup` mounts a
   fresh `devtmpfs` on `/dev`, which a user namespace (rootless
   container) can never do, even with `--privileged`. As a regular user,
   mkarchiso runs pacstrap with `-N` (unshare mode), whose
   `unshare_setup` only uses bind mounts of individual device nodes plus
   proc and tmpfs, which are allowed. Fix: run mkarchiso as a `builder`
   user inside the container, in a nested user namespace.
 * **newuidmap has no file capabilities** in the archlinux image
   (`newuidmap: Could not set caps`). Fix: `setcap cap_setuid=ep
   /usr/bin/newuidmap` and `cap_setgid=ep /usr/bin/newgidmap`.
 * **Mapping container uid 0 needs CAP_SETFCAP.** A subuid range that
   included container root failed the same way. The rootless container
   has uids/gids 0-65536, so `/etc/subuid` and `/etc/subgid` are
   `builder:1001:64536`, giving builder's namespace uids 1-64536
   (including `nobody`=65534) without touching container uid 0.
 * **Host ownership.** Files created by `builder` would appear on the
   host owned by a subordinate uid, so builder only writes inside the
   container and container root does `install -m 600` of the ISO into
   `secrets/out/`.

Harmless noise in the build log: `fchownat() of /dev/... failed` and
`error: command failed to execute correctly` from a pacman hook during
the container's own `pacman -Syu`, and `fchownat() of /run/rdnssd failed`
during pacstrap (build-time `/run` is a tmpfs that is not in the image;
tmpfiles recreates it at boot).

### Verification

   owned by the host user, mode 600.
 * Compared `unsquashfs -lln` of the container-built ISO with the
   previous native build: same 99458 paths with identical owner, group
   and mode for every one.

## `just inspect`: check what's in an ISO

```
just inspect                       # newest ISO in secrets/out/
just inspect secrets/out/<file>.iso
```

`inspect.sh` uses the same host/container pattern as `build.sh`: on the
host it runs the archlinux container (no `--privileged`), mounting only
itself and the chosen ISO read-only, plus the pacman cache volume. In
the container it installs `squashfs-tools`, extracts
`arch/x86_64/airootfs.sfs` with `bsdtar`, and prints:

 * the ISO name/size, `IMAGE_ID`/`IMAGE_VERSION`, and hostname;
 * owner and mode (never contents) of the secret paths
   (`/etc/wireguard`, `/var/lib/iwd`, `/root/.ssh`, `/etc/arch-iso`,
   SSH host private keys) and of our overlay files and enable symlinks;
 * `PASS`, or `FAIL` (exit 1) listing any regular file under a secret
   path that is not `0/0` or has group/other permission bits.

Bugs found while writing it: the path regex was anchored after a space
(matched nothing); a non-matching `grep` aborted the script under
`pipefail`; symlink lines end in `-> target`, so the path is field 6
(not the last field) and the path must also be allowed to end at a
space. The FAIL filter was checked against sample lines (group-readable,
non-root owner, world-readable) and flags each of them.

Output on the current ISO: all secrets `0/0` mode 600 in 700 dirs
(including `/etc/arch-iso/webhook.env`, now that `WEBHOOK_URL` is set),
both enable symlinks present, `PASS`.

## Raspberry Pi 5 target (`just build-rpi5`)

Goal: the same live installer for a Raspberry Pi 5 whose NVMe drive is
hard to take out. Boot it from a USB stick or SD card, SSH in over the
VPN, and `pacstrap` Arch Linux ARM (ALARM) onto the NVMe. Same repo,
same `secrets/` (one WireGuard key and one set of SSH host keys: both
images are "the arch-iso installer"). Built on an Apple Silicon Mac, so
the arm64 build runs natively.

Decisions:

 * **archiso, not Alpine.** archiso 91 supports aarch64 (releng ships
   `packages.aarch64`), and its initcpio hooks (`mkinitcpio-archiso`,
   packaged by ALARM) are arch-independent: they find the boot device
   by label or UUID, mount `${archisobasedir}/$(uname -m)/airootfs.sfs`,
   and copy it to RAM when it is < 4 GiB and RAM > image + 2 GiB. So
   the live system is Arch with systemd like the ISO, `airootfs/` and
   the secrets staging are reused unchanged, and installing is
   `pacstrap`.
 * **No boot loader.** The Pi 5 firmware lives in its EEPROM and boots
   a FAT partition directly (`config.txt`, `kernel8.img`, initramfs,
   DTBs, `cmdline.txt`). mkarchiso runs in **netboot** mode, which
   stops after kernel + initramfs + `airootfs.sfs`; `build.sh` packs
   those and the airootfs's `/boot` into an MBR disk image with one
   FAT32 (LBA, bootable) partition at 1 MiB.
 * **Kernel `linux-rpi-16k`** (Raspberry Pi Foundation fork, 16K pages,
   bcm2712 only). ALARM's generic `linux-aarch64` boots via U-Boot and
   does not support the Pi 5. The package installs `kernel8.img` and a
   `config.txt` with `initramfs initramfs-linux.img followkernel`.
 * **Boot partition lookup:** a random FAT volume ID per build,
   passed as `archisosearchuuid=XXXX-XXXX` in `cmdline.txt` (plus the
   `/boot/XXXX-XXXX.uuid` search file), like the ISO's search UUID.
 * **Build container:** there is no official ALARM image. `build.sh`
   downloads `ArchLinuxARM-aarch64-latest.tar.gz` once, verifies its
   signature in a throwaway Debian container against the pinned ALARM
   build key `68B3537F39A313B3E574D06777193F152BDBE6A6`, and imports
   it as `localhost/archlinuxarm:latest`. ALARM doesn't package
   archiso, so Arch's (arch `any`) is installed with `pacman -U` from
   the URL that `archlinux.org/packages/extra/any/archiso/download/`
   redirects to (signature checked with ALARM's `archlinux-keyring`).
 * **Package list:** releng's `packages.aarch64` + `packages.extra` +
   `packages.rpi5` (which also removes `linux`, `linux-dtbs`, `stubble`,
   `grub`, `edk2-shell`, `efibootmgr` and adds `linux-rpi-16k`,
   `firmware-raspberrypi`, `rpi5-eeprom`, `raspberrypi-utils`).
   Anything ALARM doesn't have is skipped with a message (currently
   only `ghostty-terminfo`).
 * Each target refuses to build on a Podman host of the other
   architecture (emulation would take hours). (Superseded: see "Cross
   builds" below.)

Setup on the Mac (2026-10-24):

```
brew install podman            # 6.1.4
podman machine init --cpus 4 --memory 3072 --disk-size 60
podman machine start           # Fedora CoreOS VM, arm64, rootless
```

The VM maps container uids 0-1000000, so `setup_builder`'s
`builder:1001:64536` subuid range works as on Linux.

### Problems hit and fixes

 * **`config.sh` failed on macOS:** BSD `install` can't read
   `/dev/stdin`. Now `mkdir -p` + `cat` under `umask 077`.
 * **pacman's download sandbox** (Landlock + `DownloadUser = alpm`)
   fails in an unprivileged container. The build container already
   runs `--privileged`, where it works; for pacstrap in builder's
   nested namespace the profile's `pacman.conf` (a copy of ALARM's)
   sets `DisableSandbox` and comments out `DownloadUser`. `inspect.sh`
   uses `pacman --disable-sandbox`.
 * **mkarchiso expects `/boot/vmlinuz-*`.** A build-only pacman hook
   (`rpi5/airootfs/etc/pacman.d/hooks/90-archiso-rpi-vmlinuz.hook`,
   marked `# remove from airootfs!` so releng's zzzz99 hook deletes
   it) copies `kernel8.img` to `vmlinuz-linux-rpi-16k`. The copy is
   left off the FAT partition.
 * **`useradd: UID 1000 is not unique`:** the ALARM rootfs has an
   `alarm` user with uid 1000. Removed in the container before
   `setup_builder`.
 * Sourcing `profiledef.sh` for the image name needs `declare -A
   file_permissions` first (it assigns string keys).
 * The disk image is assembled without loop devices: `mkfs.vfat -C`
   into a file, `mcopy -s`, `sfdisk` on the image file, `dd` the FAT in
   at 1 MiB.

### Verification (test secrets in a scratch copy: throwaway SSH key, no WireGuard/WiFi/webhook)

 * `./build.sh rpi5` succeeded in ~10 minutes (first run of the final
   version; package cache warm from an earlier attempt). Most of it is
   xz-compressing the squashfs (~75k inodes). Output:

### First attempt: run the whole build container under emulation

`podman run --arch <target>` with qemu-user via binfmt_misc. Tested on
the Mac (x86_64 ISO in an emulated `archlinux` container). Two failures:

 * pacman: `error restricting syscalls via seccomp: 22` and `switching
   to sandbox user 'alpm' failed`: qemu-user can't apply pacman's
   download sandbox (worked around with `--disable-sandbox`).
 * Then `unshare failed: Invalid argument` when builder creates its user
   namespace. qemu-user is multithreaded, and the kernel refuses
   `unshare(CLONE_NEWUSER)` from a multithreaded process. This is not
   fixable with binfmt flags, so rootless mkarchiso can't run in an
   emulated container at all. (I had guessed it was the missing C
   flag on Arch's binfmt entries; that was wrong.)

### Design: native container, foreign-arch pacstrap

The build container now always matches the **host**: `archlinux` on
amd64, the imported `localhost/archlinuxarm` on arm64. The target
architecture only appears in the profile's `pacman.conf`
(`Architecture = x86_64|aarch64`), so pacman, the nested user
namespace, mksquashfs, xorriso, mkfs.vfat etc. all run natively. Only
the target's binaries run in the image root (scriptlets, pacman hooks,
mkinitcpio, the vmlinuz hook) go through qemu-user, which needs just
the binfmt **F** flag (standard in the qemu-user-static packages).

 * `rpi5/pacman.conf`: ALARM's repos for aarch64, used by both kinds of
   container (previously a copy of the ALARM container's own).
 * x86_64 on arm64: releng's `pacman.conf` gets `Architecture = x86_64`
   and an Arch mirror instead of the container's (ALARM) mirrorlist.
   ALARM's container already has `archlinux-keyring`.
 * rpi5 on amd64: the container trusts the pinned ALARM build key
   (`pacman-key --recv-keys` + `--lsign-key`).
 * Cross builds put the target's packages in
   `/var/cache/pacman/pkg/<arch>/` (profile `CacheDir`), apart from the
   container's: both distros have `any` packages with the same file
   names and different signatures.
 * `rpi5_packages` checks availability against the target repos, synced
   with the profile's `pacman.conf` into a throwaway database.
 * Cache volumes are per host: `archiso-wireguard-pacman-cache` (amd64,
   unchanged) and `archiso-wireguard-pacman-cache-arm64`.
 * `inspect.sh` also uses the host's container (both inspect both image
   types).
 * The host checks that a target-arch binary runs (`busybox` image with
   `--arch`) before starting, and says it is a cross build.

Problem hit: mkarchiso takes `arch` from `uname -m` when the profile
doesn't set it, so the cross ISO build tried to install the aarch64
list. `build.sh` now sets `arch="x86_64"` for the ISO too.

 * **x86_64 ISO on arm64** (cross): succeeded in ~17.5 minutes with an

 * **rpi5 on arm64** (native) after the rework: succeeded in ~10

## One stick for both: `just build-usb`

Goal: a single USB stick that boots x86_64 PCs and the Raspberry Pi 5.

Why it fits on one FAT32 partition: the Pi 5 firmware reads only the
top-level files (`config.txt`, `kernel8.img`, initramfs, DTBs,
`overlays/`, `cmdline.txt`); x86_64 UEFI firmware runs
`EFI/BOOT/BOOTx64.EFI` (systemd-boot), which reads `loader/entries/`
and loads `arch/boot/x86_64/`; and archiso's initramfs mounts
`arch/$(uname -m)/airootfs.sfs`, so `arch/x86_64/` and `arch/aarch64/`
coexist. The ISO's initramfs looks for its ISO volume UUID first, then
for the file `/boot/<uuid>.uuid` on every partition, which is how
archiso supports copying an ISO onto a FAT32 stick.

Implementation (`build.sh usb`):

 * Host side: run `build.sh x86_64` (its own container), then the rpi5
   build with the new ISO's path in `ARCHISO_WIREGUARD_USB_ISO`.
 * `usb` builds exactly like `rpi5` (`pi_target`); in
   `make_rpi5_image` it also extracts the ISO into the FAT staging with
   `bsdtar`, except the ISO 9660-only `boot/syslinux`, `boot/grub` and
   `arch/grubenv`, and checks `EFI/BOOT/BOOTx64.EFI` and
   `arch/x86_64/` are there.
 * Output: `arch-usb-CONTAINS-SECRETS-<date>-x86_64+rpi5.img`; the ISO
   is kept.
 * `inspect.sh` now inspects every `arch/*/airootfs.sfs` in an image
   (an ISO or rpi5 image has one, a usb image two).

Decisions: UEFI only on x86_64 (legacy BIOS would need syslinux in the
FAT partition and MBR boot code; possible, not done). Partition type
stays `0x0c`, which the Pi needs; most UEFI firmware boots FAT32 USB
sticks of that type, a strict one may want `0xef`.

### Verification (Mac, test secrets)

 * `./build.sh usb` succeeded in ~25 minutes (cross x86_64 ISO, warm
   cache, then native rpi5). Image 2.5 GB, one bootable FAT32 (LBA)
   partition.
 * `inspect.sh`: `arch/x86_64` (`IMAGE_ID=arch-iso-CONTAINS-SECRETS`)
   and `arch/aarch64` (`arch-rpi5-CONTAINS-SECRETS`) both PASS.
 * FAT contents: `EFI/BOOT/BOOTx64.EFI` + `BOOTIA32.EFI`,
   `loader/loader.conf` + entries, `arch/boot/x86_64/` kernel and
   initramfs, both airootfs, `boot/<iso uuid>.uuid` matching the loader
   entry's `archisosearchuuid`, `boot/<fat volid>.uuid` matching
   `cmdline.txt`; no syslinux or grub.
 * Both builds write `arch/version`; the ISO's wins. Informational only.

### Tested on hardware (2026-10-24)

The user built `just build-usb` with the real secrets, wrote it to a USB
stick, and **booted it on an x86_64 PC (UEFI) and on the Raspberry Pi
5**.

 * First Pi attempt booted the NVMe instead: its `BOOT_ORDER=0xf461`
   tries SD, NVMe, then USB, so a bootable NVMe always wins. With
   `BOOT_ORDER=0xf641` (SD, USB, NVMe) the stick boots, and without it
   the Pi falls through to the NVMe.
 * While debugging, found that the FAT boot sector's "hidden sectors"
   field was 0 (`mkfs.vfat -C` formats a plain file, but the partition
   starts at sector 2048). The Pi booted anyway, so its bootloader
   doesn't rely on it; `build.sh` now passes `-h 2048` so the field is
   correct for any firmware that does. Built images with this change
   are not yet boot-tested.

## Generic images: configuration moves to the stick (2026-10-24)

Until now every secret was baked into the squashfs at build time, so
each image was personal, could not be shared, and any change (a new
WiFi network, a new key) meant a full rebuild. The FAT32 partition the
usb and rpi5 images boot from is writable, and archiso leaves it
mounted in the running system, so the secrets can live there instead.

Decision: **no baked-in secrets at all**. The build takes no input and
produces a generic image; the user fills in `archiso-config/` on the
stick after writing it. `CONTAINS-SECRETS` is gone from the image
names, and the output moved from `secrets/out/` to `out/`.

### What the live system does

`airootfs/usr/local/bin/arch-iso-config`, run by
`arch-iso-config.service` (`Before=sysinit.target`, so ahead of iwd,
`wg-quick@wg0`, `sshd`, `sshdgenkeys` and the webhook), copies the
config into the tmpfs root with the modes the old `file_permissions`
entries used to set:

```
wifi/*.psk          -> /var/lib/iwd/           700 dir, 600 files
wireguard/wg0.conf  -> /etc/wireguard/         700 dir, 600 file
ssh/authorized_keys -> /root/.ssh/             700 dir, 600 file
webhook.env         -> /etc/arch-iso/          700 dir, 600 file
ssh/host/*          -> /etc/ssh/               600 keys, 644 .pub
```

Where it reads from:

 * `/run/archiso/bootmnt/archiso-config` when it exists. archiso's
   initcpio hook mounts the boot device there read-only
   (`_mnt_dev "${archisodevice}" "/run/archiso/bootmnt" "-r"`,
   `/usr/lib/initcpio/hooks/archiso:270` in mkinitcpio-archiso) and
   `/run` survives `switch_root`, so it is still there in the live
   system.
 * Otherwise any filesystem labelled `ARCH_CONFIG`, mounted (rw if
   possible, `umask=0077`) and unmounted again. The usb/rpi5 FAT label
   changed from `ARCH_RPI5` to `ARCH_CONFIG` for this.

The fallback turned out to be the **normal** path, not the edge case.
Booting the test image in QEMU with 4 GB of RAM, the loader reported
`Configuration: /run/arch-iso/config/archiso-config`, and `findmnt` in
the live system showed no `/run/archiso/bootmnt` at all, but a
`/run/archiso/copytoram` tmpfs: releng boots `copytoram=auto`, so a
machine with enough RAM copies the live system to RAM and the hook
unmounts the boot partition before `switch_root`
(`/usr/lib/initcpio/hooks/archiso:378`). `bootmnt` only survives on a
machine too small for that, or with `copytoram=n`. Both paths are
exercised below. The practical consequence: **the `ARCH_CONFIG` label
is load-bearing** on every target, not just the ISO, and relabelling a
stick makes it boot unconfigured.

Missing or fully commented-out files are not errors: the feature is
skipped and boot continues. `wg-quick@wg0` is now always enabled, with
a `ConditionPathExists=/etc/wireguard/wg0.conf` drop-in instead of the
build deleting its enable symlink.

### SSH host keys

The one piece that can't ship in a generic image: a shared private host
key would let anyone with the image MITM anyone else's machine. They
are generated on the first boot and written back to
`archiso-config/ssh/host/` on the stick, so the fingerprint is stable
from the second boot on. The partition is mounted read-only, so the
save remounts it rw, copies, `sync`s and remounts ro. On read-only
media the save fails with a warning and the keys are ephemeral. The
fingerprints are printed to the journal/console on every boot.

### Host side

 * `config-templates/` is now the single source of the templates:
   `config.sh` copies the missing ones into `secrets/`, and `build.sh`
   copies the whole tree onto the image's FAT partition as
   `archiso-config/`, so a freshly written stick is self-documenting
   (it includes a `README.txt`).
 * `provision.sh` (`just provision`) does what `check_secrets` used to:
   it validates `secrets/` (`[Interface]`/`PrivateKey`,
   `PersistentKeepalive`, a non-comment `authorized_keys`, warnings for
   no WiFi/webhook) and then copies it onto a mounted config partition
   (plain `cp`), or into an image file or device node with `mtools` in
   a container (`sfdisk -J` for the partition offset, `@@<bytes>` for
   mtools). Validation had to move somewhere: the target is headless,
   and a typo that used to fail the build would otherwise only show up
   as a machine that never appears.
 * `inspect.sh` flipped: it used to require that the baked-in secrets
   were root-only, and now requires that **no** file exists under
   `/etc/wireguard`, `/var/lib/iwd`, `/root/.ssh`, `/etc/arch-iso` or
   `/etc/ssh/ssh_host_*_key` in the squashfs. For an `.img` it also
   lists `archiso-config/` and, by counting non-comment lines with
   `mtype` (never printing contents), says whether the image is still
   generic or has been provisioned and must not be published.

### Trade-offs accepted

 * The config partition is plain text and world-readable on any machine
   it is plugged into, where before the secrets were inside a squashfs.
   The security boundary was already physical possession of the stick;
   it is just more visible now. FAT has no ownership, so the modes are
   applied on copy into the tmpfs instead.
 * The plain ISO (`just build`) can no longer carry its own
   configuration at all: ISO 9660 is read-only, so it needs a second
   `ARCH_CONFIG` filesystem. `just build-usb` is the recommended path.
 * A stick provisioned by `provision.sh` before `dd` is no longer a
   generic image; `just inspect` says so.

Containers:

## Every target is a configurable disk image (2026-10-24)

`just build` still produced a plain ISO, which after the previous
change was the one deliverable that could not be configured: ISO 9660
is read-only, so the stick had no `archiso-config/` and the live system
came up with no keys, no WiFi and no VPN — the stock Arch installer.
`just build-rpi5` was fine (its FAT32 partition always carried the
config), but the ISO was not.

Decision: **no BIOS support**, so the ISO stops being a deliverable.
`just build` now produces an x86_64 UEFI disk image — the usb image
minus the Pi half — and every target is one MBR disk image with a
single FAT32 partition carrying the live system and `archiso-config/`.

 * `make_rpi5_image` became `make_disk_image`, which assembles the FAT
   from the Pi's `/boot` + netboot airootfs (rpi5), from an ISO's UEFI
   boot files + `arch/x86_64/` (x86_64), or both (usb). `cmdline.txt`
   and the `/boot/<uuid>.uuid` search file are only written for Pi
   targets: on x86_64 systemd-boot's loader entry already carries the
   ISO's search UUID, and the ISO's own `.uuid` file comes along with
   the extraction.
 * A new internal target, `build.sh iso`, builds the plain ISO into
   `out/.iso-stage/` for the usb target to merge; `run_usb` deletes it
   afterwards. For the x86_64 target the ISO never leaves the
   container: one `mkarchiso` run, then `make_disk_image` packs it.
 * `archiso` depends on `dosfstools` and `mtools`, so the x86_64
   container already has what the packing needs.
 * `inspect.sh` only prints `Boot:` when the image has a `cmdline.txt`
   (Pi targets).

Why not go further and keep only `just build-usb`, as first suggested:
a hybrid image needs both architectures, so it needs qemu-user on
whichever one the host isn't. Dropping the single-architecture targets
would mean no build at all is possible on a host without binfmt_misc
set up — including the machine this was developed on. `just build` on
x86_64 and `just build-rpi5` on arm64 stay native.

What is lost: legacy BIOS boot, which only the ISO could do.

### Verification

`just build` produced `arch-iso-2026.10.25-x86_64.img`, 1.4 GB (the
1.6 GB ISO minus syslinux and grub), and `just inspect` reported no
secrets, the overlay, and "the config partition holds only the

A copy was provisioned with `provision.sh` (mtools, into the image) and

## rpi5 and usb cross-built on an x86_64 host (2026-10-24)

The combination LOG.md kept listing as untested -- a Pi image built on
an amd64 host -- failed as soon as a host with aarch64 binfmt existed:

```
gpg: key 77193F152BDBE6A6: public key "Arch Linux ARM Build System ..." imported
==> ERROR: There is no secret key available to sign with.
==> Use 'pacman-key --init' to generate a default secret key.
```

`build_iso` only ran `pacman-key --init` on the aarch64 path, inside

the container's mount namespace, where /nix/store does not exist.

## `just provision` defaults to the stick, not an image (2026-10-24)

The no-argument default was the newest image in `out/`, which is the
wrong end of the pipeline: the documented flow is build -> dd -> edit
the stick, and provisioning the image instead silently turns a generic
image into one carrying secrets.

With no argument it now finds the stick:
`findmnt -rn -o TARGET -S LABEL=ARCH_CONFIG` picks up whatever a
desktop automounter left at e.g. `/run/media/you/ARCH_CONFIG`. If the
label exists but is not mounted, `blkid -L` reports where it is instead
of guessing. Naming a target explicitly still works for a mount point,
a `/dev` node or an image, and the image case now says the image is no
longer generic.

Tested: no stick -> the error names what to do; a mounted stick (stubbed
`findmnt`, since nothing on the dev host carries a filesystem label) ->
`archiso-config/` written to it, including an SSID with a space; an
explicit `.img` -> written via mtools with the not-generic warning.

## `just provision` mounts the stick itself (2026-10-24)

Mounting the config partition by hand is a trap, and the first attempt
on real hardware hit it: FAT stores no ownership, so the vfat driver
makes it up from mount options, and `sudo mount` defaults to `uid=0`.
The stick mounts, and then the files it exists to let you edit are
root-owned and unwritable as your own user.

`udisksctl mount -b /dev/sdX1` is the answer -- udisks passes
`uid=<caller>,gid=<caller>` and mounts under `/run/media/<user>/` with
no root at all:

```
rw,nosuid,nodev,relatime,uid=1000,gid=100,fmask=0022,dmask=0022,...
```

So `find_target` now does that itself when it finds the `ARCH_CONFIG`
label unmounted, records the device in `MOUNTED_DEV`, and unmounts it
again on the way out (via an EXIT trap, so a failure part-way through
still releases the stick). A partition the user had already mounted is
used as-is and left alone. README step 4 documents the `udisksctl` line
and why `sudo mount` is wrong.

`find_target` had to stop returning its answer on stdout for this: it
was called as `target=$(find_target)`, and a `$( )` subshell would have
thrown `MOUNTED_DEV` away. It sets `TARGET` instead.

One bug caught by testing: `TARGET=$(findmnt ... -S LABEL=...)` exits 1
when nothing is mounted, and under `set -e` that ended the script
before the unmounted-device fallback could run -- the first run printed
nothing at all and exited 1. The query is now a `label_mountpoint`
helper called with `|| true`.

Tested with `udisksctl loop-setup` on a FAT image labelled `TESTCFG`
(not `ARCH_CONFIG`, to keep the real stick out of it): unmounted label
-> mounted, written, unmounted; already-mounted label -> used and left
mounted; missing label -> clean error.

## setup: the install as a command (2026-10-26)

The Arch Workstation book installs a machine from this stick in about
ninety copy-pasted blocks. `airootfs/usr/local/bin/setup` runs the same
steps, in the same order, from a host file:

 * `setup host` asks for the hostname, disk, LUKS, swap size, time
   zone, locale, keymap and whether `admin` gets passwordless sudo,
   and writes them to `/root/arch/host.env`. It seeds the rest of a
   *host repo* there (`packages.txt`, `units.txt`, `etc/` with the
   `.network` files, the sshd hardening drop-in and the sudoers drop-in,
   and `authorized_keys` copied from the stick) and commits it.
   `--from` takes a git URL, a host file, or a name looked up as
   `archiso-config/hosts/<name>.env` on the config partition.
 * The disk is recorded by its `/dev/disk/by-id/` name. The disk the
   stick is on (found by the `ARCH_CONFIG` label and by
   `/run/archiso/bootmnt`) is never offered and never accepted.
 * `setup disk` shows a review, needs the hostname typed (or
   `--confirm-wipe HOSTNAME`), then runs sgdisk, `wipefs` on the new
   partitions, optional LUKS2, mkfs, the six subvolumes, the mounts and
   the swapfile. The `wipefs` is not in the book: without it, a
   reinstall over the same layout finds the old btrfs signature where
   the new partition starts and `mkfs.btrfs` refuses. If `/mnt` already
   has the layout it does nothing; `--mount` re-mounts an existing one.
 * `setup install` picks the kernel and microcode from the hardware as
   the book does, adds `packages.txt`, and runs pacstrap (dropping `-K`
   on a Pi stick that did not ship Arch Linux ARM's keyring), writes
   rather than appends the fstab, sets the locale and hostname, adds
   `sd-encrypt` when encrypted, writes the systemd-boot entry or the
   Pi's `cmdline.txt` from UUIDs it reads, applies the host repo's
   `etc/` and `units.txt` into `/mnt`, links `resolv.conf` and copies
   the iwd networks from outside the chroot, creates `admin` and
   `user`, checks sudoers with `visudo -c`, installs `authorized_keys`,
   asks for the three passwords (skipping any already set), and copies
   the host repo to `/home/admin/arch`.
 * `setup check` is the book's pre-flight check, judged rather than
   printed: any failing line makes it exit non-zero, and
   `setup reboot` will not unmount or reboot until it passes.
 * git keeps no file modes, so `apply` sets them by place (sudoers
   drop-ins 0440, everything else 0644).
 * `git` is added to `packages.extra`, for `--from <git URL>` and the
   host repo.
 * `just provision` copies `setup` to `archiso-config/bin/setup`, and
   `arch-iso-config` installs that over the copy in the image, so the
   installer can be updated without rebuilding the image.

Tested so far: `bash -n` and shellcheck are clean. `setup disk` was run
against a 12 GB loopback disk in an Ubuntu container (fresh, re-run as
a no-op, unmounted and `--mount`ed again), with two substitutions the
container forced: ext4 for the ESP (no vfat module) and a no-op
`udevadm`. LUKS formatted but could not be opened there (no
device-mapper). `setup host` was exercised for the files it writes;
`setup install`, `check` and `reboot` have not been run yet, because
they need an Arch live system.

## Unattended test: just test-vm (2026-10-26)

 * `setup install --passwords FILE` takes `name:password` or
   `name:$6$...` lines for root, admin and user and sets them with
   `chpasswd` (`-e` for hashes) instead of prompting; the line is not
   echoed. With `--yes` and `setup disk --confirm-wipe HOSTNAME`, the
   whole install needs no input.
 * `test-vm.sh` (`just test-vm [IMAGE]`) clones the newest x86_64 image
   into `test/` (`cp -c` on APFS, `--reflink=auto` elsewhere),
   provisions the copy with a throwaway ed25519 key through
   `provision.sh` (which now honours `BOOMSTICK_SECRETS`), and boots it
   in QEMU: q35, UEFI from qemu's own edk2 files or the distribution's
   OVMF, the stick as USB storage, a blank 20 GB qcow2 as a virtio disk
   with serial `setuptest` (so `/dev/disk/by-id/virtio-setuptest`),
   user networking with sshd forwarded to localhost:2222, and
   `-no-reboot` so a reboot ends the QEMU process.
 * Over SSH it copies this tree's `setup` over the image's (so the
   image does not need rebuilding to test a change), then runs
   `setup host --from`, `setup --yes disk --confirm-wipe setuptest`,
   `setup --yes install --passwords`, and `setup --yes reboot`. It boots
   the installed disk alone, logs in as `admin`, checks the hostname,
   the `@` and `@home` mounts, swap, passwordless sudo, `user` outside
   `wheel`, sshd's effective `permitrootlogin` and
   `passwordauthentication`, the host repo's owner and failed units,
   then powers off and prints PASS.
 * KVM on an x86_64 Linux host, TCG elsewhere, so on Apple Silicon it
   is slow. `ENCRYPT=yes` types the LUKS passphrase over a pty and stops
   after the install, since nothing types it at the next boot yet.
 * Not run yet. An attempt to build the image and run it in a cloud
   container failed at the first `pacman -Sy`: that container has no
   direct DNS, only an HTTPS proxy.

## Running just test-vm on Apple Silicon (2026-10-26)

 * `just build` failed at once with "./build.sh: Permission denied":
   "Add setup" had committed `build.sh` as 100644, dropping its
   executable bit. Restored to 100755.
 * `just test-vm` then failed provisioning the test stick: "Public
   keyring not found ... required key missing from keyring". On arm64
   `provision.sh` runs in the imported Arch Linux ARM image, which has
   no pacman keyring until someone runs `pacman-key --init`; build.sh
   and inspect.sh do, provision.sh did not (it was only ever run on
   amd64, where the official image ships one). It now initializes and
   populates the keyring first, as inspect.sh does.
 * On NixOS, test-vm found no UEFI firmware: qemu-system-x86_64 is a
   link from /run/current-system/sw/bin, where ../share/qemu is not
   there. It now also looks next to the resolved binary (qemu's store
   path, which has edk2-x86_64-code.fd), and FW_CODE/FW_VARS name the
   firmware files directly when they are elsewhere.
 * The first full run on Apple Silicon installed, rebooted and logged
   in as admin (10m31s under TCG), then failed two checks: "root cannot
   ssh" and "passwords are refused". The system was right, the test was
   not: OpenSSH 10.6's `sshd -T` prints keywords in their configuration
   case (`PermitRootLogin no`), where older versions printed them in
   lower case, and the test grepped for `permitrootlogin no` exactly.
   It now matches without regard to case (`grep -qix`).
